# Q : 바이브 코딩(Vibe Coding)이란 무엇이고, 왜 지금 배워야 하나요?

<br />

# A : 바이브 코딩은 코드를 한 줄씩 직접 쓰는 대신 **AI에게 자연어로 원하는 것을 말하고, 결과를 실행해 보며 계속 요청을 고쳐 가는 방식**의 개발입니다. 2025년 2월 Andrej Karpathy가 "분위기(vibe)에 완전히 몸을 맡기고, 코드가 존재한다는 것조차 잊는" 코딩이라고 부르면서 퍼졌고, 2025년 Collins 사전 올해의 단어로 뽑혔습니다. 원래 뜻은 **AI가 쓴 코드를 검토하지 않고 결과만 보고 받아들이는 것**이라서, 주말 장난감 프로젝트나 프로토타입에는 훌륭하지만 운영 서비스에 그대로 쓰면 위험합니다. 그래서 지금 배워야 하는 이유는 "코드를 안 봐도 된다"가 아니라, **아이디어를 몇 시간 안에 동작하는 결과물로 만드는 속도**를 얻고, 동시에 **AI가 만든 코드를 읽고 검증하고 설명할 수 있는 능력**이 개발자의 핵심 역량이 되었기 때문입니다.

### 어디서 나온 말인가

- 2025년 2월 Karpathy(OpenAI 공동 창업자, 전 Tesla AI 책임자)가 처음 썼다. 그는 이 방식이 **"버려도 되는 주말 프로젝트에는 나쁘지 않다"**고 했다.
- 그 전에도 Karpathy는 2023년 "가장 인기 있는 새 프로그래밍 언어는 영어"라고 말한 적이 있다.
- 2025년 3월 Merriam-Webster가 신조어로 올렸고, 2025년 Collins 사전 올해의 단어가 됐다.
- 이후 뜻이 넓어져서 "AI로 코드를 짜는 모든 것"을 바이브 코딩이라 부르는 경우도 많아졌다. 이 부분은 논쟁이 있다.

### 바이브 코딩 vs AI를 활용한 개발

Simon Willison은 둘을 구분해야 한다고 강조한다.

| | 바이브 코딩 | AI를 활용한 개발 |
|---|---|---|
| 정의 | AI가 쓴 코드를 **검토하지 않고** 결과만 보고 진행 | AI가 쓴 코드를 **읽고, 테스트하고, 설명할 수 있는** 상태로 만들기 |
| 확인 방법 | "돌아가네?" | 코드 리뷰, 테스트, 타입 검사 |
| 잘 맞는 곳 | 프로토타입, 개인 도구, 학습, 아이디어 검증 | 운영 서비스, 팀 코드베이스 |
| 위험 | 숨은 버그·보안 구멍을 모름 | 상대적으로 낮음 |

- Willison의 원칙: **"다른 사람에게 정확히 무엇을 하는지 설명할 수 없는 코드는 커밋하지 않는다."** AI가 썼더라도 내가 리뷰·테스트하고 설명할 수 있으면 그건 바이브 코딩이 아니라 그냥 소프트웨어 개발이다.

### 바이브 코딩을 해도 되는 경우 (Willison의 체크리스트)

- **잘못돼도 큰일 나지 않는 프로젝트인가?** 버그나 보안 문제로 누군가 피해를 볼 수 있으면 안 된다.
- **비밀값이 노출되지 않는가?** API 키를 코드나 프롬프트에 그대로 넣지 않는다.
- **개인정보를 넣지 않는가?** 민감한 데이터를 외부 도구에 붙여 넣지 않는다.
- **다른 서비스에 부담을 주지 않는가?** 무한 요청, 과도한 크롤링.
- **돈이 새지 않는가?** 사용량 한도가 없는 유료 API를 그대로 쓰지 않는다.
- 처음이라면 샌드박스에서 하고, 남에게 공유하기 전에 경험자에게 한 번 확인받는다.

### 실제로 생긴 문제들

| 사례 | 내용 |
|---|---|
| 보안 | 2025년 5월, 한 AI 앱 빌더(Lovable)로 만든 웹앱 1,645개 중 170개에서 누구나 개인정보에 접근할 수 있는 문제가 발견됨 |
| 데이터 삭제 | 2025년 7월, "변경하지 말라"고 지시했는데도 AI 에이전트(Replit)가 데이터베이스를 삭제한 사례가 보고됨 |
| 코드 품질 | 2025년 12월 CodeRabbit 분석: AI가 함께 쓴 PR에서 중대한 문제가 약 1.7배, 보안 취약점이 2.74배 많았음 |
| 생산성 착각 | 2025년 7월 METR 실험: AI 도구를 쓴 개발자들이 **스스로는 빨라졌다고 느꼈지만 실제로는 19% 느렸음** |
| 유지보수 | 리팩터링 비율은 줄고 복사·붙여넣기 코드가 늘었다는 분석(GitClear). 직접 쓰지 않은 코드는 나중에 이해하기 어렵다 |

### 그래도 왜 지금 배워야 하나

1. **아이디어 → 결과물의 속도.** 프로토타입, 사내 도구, 데모, 디자인 시안 확인은 몇 시간 만에 동작하는 형태로 만들 수 있다. "일단 만들어 보고 판단"이 가능해진다.
2. **개발자의 역할이 바뀌고 있다.** 직접 타이핑하는 비중은 줄고, **무엇을 만들지 명확히 설명하고, 결과를 검증하고, 구조를 잡는 일**의 비중이 커졌다. 이건 바이브 코딩을 직접 해 봐야 감이 생긴다.
3. **AI가 잘하는 것과 못하는 것을 알아야 한다.** 써 봐야 어디서 그럴듯한 틀린 코드를 만드는지, 어떤 요청이 잘 통하는지 안다.
4. **비개발자도 만들기 시작했다.** 기획자·디자이너가 바이브 코딩으로 만든 프로토타입을 운영 수준으로 옮기는 일, 거기서 생긴 보안·품질 문제를 잡는 일이 개발자에게 온다.
5. **반대로 기본기의 가치가 커졌다.** 위 사례처럼 검증 없이 쌓인 코드는 결국 문제를 만든다. 코드를 읽고, 테스트를 설계하고, 보안 구멍을 찾는 능력이 있어야 AI의 속도를 안전하게 쓸 수 있다.

### 프론트엔드 개발자가 잘 쓰는 법

- **프로토타입은 과감하게**: 새 UI 아이디어, 애니메이션 실험, 관리자용 도구는 바이브 코딩으로 빠르게 만들어 보고 판단한다.
- **운영 코드로 옮길 때는 AI 활용 개발로 전환**: 리뷰, 테스트, 접근성 확인, 성능 측정.
- **맥락을 주고 작게 요청**: 규칙 파일(CLAUDE.md, AGENTS.md)에 스택·스타일·금지 사항을 적어 두고, 한 번에 화면 전체보다 컴포넌트 단위로 요청한다.
- **스스로 확인할 수단을 준다**: 테스트, 타입 검사, 브라우저에서 결과 확인.
- **보안 기본기는 내가 챙긴다**: 키는 서버에만, 권한은 서버에서 확인, 출력은 sanitize.

- 면접 답변 요약: "바이브 코딩은 AI에게 자연어로 요청하고 결과를 보며 계속 고쳐 가는 방식으로, 원래는 AI가 쓴 코드를 검토하지 않고 받아들이는 것을 말합니다. 프로토타입이나 개인 도구처럼 위험이 낮은 곳에서는 아이디어를 몇 시간 만에 결과물로 만들 수 있어 강력하지만, 운영 코드에서는 보안 구멍이나 유지보수 문제가 실제로 보고되고 있습니다. 그래서 저는 실험 단계에서는 바이브 코딩으로 빠르게 검증하고, 운영 코드로 옮길 때는 리뷰·테스트를 거쳐 제가 설명할 수 있는 코드만 커밋합니다. 지금 배워야 하는 이유는 이 속도를 얻는 동시에, AI가 만든 코드를 검증하는 능력이 개발자의 핵심 역량이 되었기 때문입니다."
